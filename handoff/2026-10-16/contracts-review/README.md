## Четыре изменения

1. **Gateway — единственная точка durable-записи** через адаптер 2.3. Runner создаёт локальный checkpoint и сообщает metadata; не пишет в центральную БД/Git-as-Storage. Локальный Git runner не равен центральному подтверждению.
2. **outcome_unknown — терминал.** Сверяется операция записи; позднее подтверждение не меняет status/revision/ленту закрытого Run. В одном Run ровно одно последнее терминальное событие.
3. **Один events.v0:** waiting_for_input, исходный конверт snake_case, questions[] и answers map, дедупликация event_id до seq. CamelCase WEB — проекция, не новая схема событий.
4. **Стабильный документ → immutable-версии.** Доработка после completed создаёт новый связанный Run в том же проекте. Approval — отдельный идемпотентный receipt конкретной версии, не событие закрытого Run и не подтверждение сохранения.

## Как принять правки после ревью

В соответствующем изолированном checkout сначала проверить blob исходного целевого файла (таблица выше), затем отдельно выполнить git apply --check для нужного patch. Только после разрешения владельца документа применить git apply и посмотреть git diff -- целевой_файл. Не применять оба патча вслепую к PPS-2 или PR #11.

Пример для ADR (пути подставляются явно):

```powershell
git -C "<checkout ADR>" hash-object --no-filters docs/adr/ADR-001-storage.md
git -C "<checkout ADR>" apply --check "<путь пакета>/ADR-001-storage.patch"
# Только после согласования:
git -C "<checkout ADR>" apply "<путь пакета>/ADR-001-storage.patch"
git -C "<checkout ADR>" diff -- docs/adr/ADR-001-storage.md
```

Для mapping — аналогично с docs/2.4/contract-mapping-web-v2.md и contract-mapping-web-v2.patch. Если blob изменился, сначала пересверить новые изменения автора; не использовать force, reset или автоматическое применение с пересчётом контекста.
