**CoreTeams — Рабочее пространство с AI-командой для сложных задач вне одной экспертизы.** Аналитический бриф с внешними источниками — тестовый артефакт этого спринта, а не новое название или определение продукта.

## Дима — подключить gateway к runner для пути CoreTeams

Карточка: **PPS-169**. Перед подключением закрыть согласование в **PPS-170** с Ильёй. Участники контракта: Дима, Илья, Арина и Катя; Филипп получает параметры развёртывания.

Результат: React отправляет задачу через gateway в реальный runner, получает состояния, уточнение и результат без ручной подмены.

Критерии приёмки:

- [ ] Сверить реально существующие history/WS операции с [предлагаемым WEB-контрактом](https://github.com/AcryCxde/PP-Sber-Autumn-2026/blob/codex/coreteams-react-handoff-2026-10-15/web-app/docs/integration.md). Выбрать согласованный transport/mapping; не считать предложенные HTTP routes уже реализованными.
- [ ] Зафиксировать общую версию полей и состояний, связь project/request/run/artifact IDs, обработку повторного запроса и ошибочного ответа.
- [ ] Проверить на реальном runner start, события, waiting_for_input, ответ в тот же run и выдачу результата. Исключить ручной запуск runner для штатного пути.
- [ ] Передавать подтверждение сохранения только после постоянной записи, согласованной с Ариной. Если записи нет или исход неизвестен, WEB не показывает успешное сохранение.
- [ ] Описать фактические интерфейсы WEB, включая загрузку сохранённого проекта; недостающий read/list API оформить как блокер, не обещать готовность восстановления на другом устройстве.
- [ ] Приложить commit/PR, обезличенное доказательство прогона и список оставшихся разрывов. Передать Кате согласованные настройки и примеры. Секреты не размещать в VITE_* или трекере.

Зависимости: согласование PPS-170, runner/CTF Ильи, persistence Арины. Проверка gateway и runner может идти до серверного деплоя, но полноценный серверный E2E зависит от Филиппа.

## Илья — провести реальный CTF Run с вопросом, результатом и ZIP

Карточка: **PPS-138**, используя результат **PPS-137**. Согласование: Дима и Арина; Катя проверяет пользовательский путь, Филипп предоставляет общий контур.

Результат: задача из WEB проходит gateway и CTF, уточнение продолжает тот же run, пользователь получает реальный аналитический результат с проверяемыми источниками.

Критерии приёмки:

- [ ] Подтвердить mapping runner/gateway, структуру question/answer/result, итоговые статусы и устойчивые IDs.
- [ ] Показать реальный вопрос и ответ без создания второго run. Ошибку и недоступность сервиса передавать явно.
- [ ] Адаптировать [skill оформления результата](../../.agents/skills/coreteams-pilot-result/SKILL.md) к CTF: `result.md`, `sources.csv`, `metadata.json`, `manifest.json`. Это готовая инструкция, ещё не доказательство регистрации skill в CTF.
- [ ] В результате отделить источники, выводы, ограничения, открытые вопросы и вклад специалистов. Не представлять AI-роли как реальных привлечённых людей.
- [ ] Проверить ZIP структурным валидатором и вручную проверить соответствие ссылок/выводов. Упаковка не доказывает истинность источников.
- [ ] В общем контуре пройти start, вопрос/ответ, результат, подтверждённое сохранение, ZIP и повторное открытие. Приложить commit/PR и обезличенную запись/протокол. До этого технический E2E — NOT_RUN или частичный.

Зависимости: gateway Димы, сохранение Арины, сервер Филиппа. Реальный пользовательский замер запускает Катя отдельно после технической готовности и согласия участника.

## Арина — передать схему постоянного хранения и контракт восстановления

Карточка: **PPS-167**. Реализацию и проверки save/restore вести в существующих **PPS-136** и **PPS-135**, не дублировать их новой задачей. Участники: Арина, Филипп, Дима, Илья и Катя.

Результат: есть согласованная схема, реализация интерфейса записи/чтения и инструкция подключения для Филиппа, позволяющие вернуться к сохранённому проекту.

Критерии приёмки:

- [ ] Зафиксировать users/projects/runs/events/artifacts/versions, ownership и выбранное место постоянного хранения. Runner-контейнер и браузерный черновик не считать постоянным серверным хранилищем.
- [ ] Сверить [требования WEB](https://github.com/AcryCxde/PP-Sber-Autumn-2026/blob/codex/coreteams-react-handoff-2026-10-15/web-app/docs/storage-requirements.md) с gateway/CTF. Описать read/list, save, download, reopen и различие proposed/approved/implemented.
- [ ] Определить момент подтверждения записи, версию артефакта, idempotency/retry и unknown write. Один повтор запроса не создаёт дублирующую версию.
- [ ] Передать Филиппу схему/миграции, mount/storage paths, имена необходимых переменных, запуск и rollback/backup. Передавать значения секретов только защищённым каналом, не через Git или описание задачи.
- [ ] В PPS-136 подтвердить доступность артефакта после завершения/очистки runner; в PPS-135 подтвердить чтение сохранённого проекта без browser localStorage, с разрешённым доступом.
- [ ] Приложить ADR/схему и commit/PR; записать, какие проверки выполнены, и получить подтверждение Филиппа о принятии инструкции. Наличие документа не равно подключению хранения.

Зависимости: решение по IDs/ownership и согласованный API с Димой/Ильёй. Схему и миграции можно готовить параллельно gateway; подключение и серверную проверку выполнять с Филиппом.

## Филипп — развернуть общий контур и открыть контролируемый тестовый доступ

Карточка: **PPS-166**, используя схему **PPS-142** и handoff **PPS-167**. Участники: Филипп, Арина, Дима, Илья и Катя.

Результат: воспроизводимое развёртывание WEB/gateway/runner/storage на командном сервере и адрес для проверки полного пути CoreTeams.

Критерии приёмки:

- [ ] Зафиксировать commit каждого компонента и воспроизводимые install/build/test команды. Локальный preview4190 на компьютере Кати не является общим сервером.
- [ ] По [инструкции WEB](https://github.com/AcryCxde/PP-Sber-Autumn-2026/blob/codex/coreteams-react-handoff-2026-10-15/web-app/docs/deployment.md) настроить CI/deploy, запуск/health checks и rollback. Перед реальным пилотом ограничить доступ.
- [ ] Подключить постоянное хранилище по схеме Арины и реальный runner/gateway Ильи/Димы. Проверить разрешённый transport, CORS/auth/ownership; не публиковать секреты в frontend.
- [ ] Подтвердить на сервере путь: проект, контекст, запуск CTF, уточнение/ответ, результат, подтверждённая запись, ZIP, восстановление проекта. Приложить версии, адрес и обезличенное доказательство, включая сбой сервиса.
- [ ] Выдать Кате тестовый URL/IP и безопасную инструкцию доступа. IP допустим для ограниченного технического теста; чувствительные данные не использовать без защищённого согласованного доступа.
- [ ] Отмечать DEPLOYMENT_READY только после полного реального прогона. Не отмечать пользовательский E2E или пользу продукта по факту успешного deploy.

Зависимости: работающий gateway/runner и принятая архитектура хранения. CI/build можно готовить параллельно, итоговая проверка блокируется отсутствующим компонентом.
