# Direction 2.5 — CoreTeams Product Web

## Goal

Produce traceable specifications, acceptance criteria, and research for CoreTeams Product Web.

## Inputs

Product repository, stakeholder brief, existing requirements, and research evidence.

## Procedure

1. Launch the GitHub plugin and inspect the relevant CoreTeams repository, branch, PR, commit, or file before proposing a specification.
2. Inspect the smallest relevant repository files; use the mapped local folder read-only through `multi-project-context` when needed.
3. When the user problem or path is unclear, use `design-thinking-experiment` or `journey-evidence-to-backlog` before narrowing scope.
4. Capture problem, users, constraints, scope, and acceptance criteria.
5. When scope includes a business-model or monetisation claim, use `monetization-unit-model` before making an economic statement.
6. Use `direction-2-5-spec-readiness` before an OpenSpec proposal to make acceptance checks, negative cases, and required human sign-off explicit.
7. Link each claim to a source or label it an assumption.
8. Record product decisions and risks in the root files.

## Done

Specification has verifiable criteria, evidence links, and a linked implementation task.
