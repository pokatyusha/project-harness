# Presentations workflow

## Goal

Prepare a defence narrative, slide structure, texts, and evidence aligned to the rubric.

## Inputs

Defence date, rubric, required format, project evidence, and reviewers' feedback.

## Procedure

1. Confirm rubric and timing.
2. For a concrete deck, record the owner-selected animation format: native PowerPoint animation or motion plan. Do not imply native motion until it has been verified in the output.
3. Use `knowledge-cat-ppt-skill` to choose the output lane and production QA; use `presentation-visual-motion` after content boundaries are known to set the project visual direction and motion plan.
4. Draft slide-by-slide message and evidence.
5. Flag unverified claims and missing proof.
6. Use `monetization-unit-model` where a business-model slide needs a bounded value or unit-economics claim.
7. Use `evidence-artifact-review` against the rubric before export or delivery.

## Canonical CoreTeams defence sequence

Always retain the name `CoreTeams` and the approved product line: `Рабочее пространство с AI-командой для сложных задач вне одной экспертизы`. The current sprint checks the user journey: task/context, run, clarification/answer, result, save/ZIP, return to project. An analytical brief is only this sprint's test artifact. Show step completion, blockers and requested help; do not turn unrun validation into a product claim.

Use this sequence for every CoreTeams defence unless the owner explicitly changes it:

1. Title and the product being defended.
2. Customer pain.
3. How the customer solves the problem today.
4. Personas.
5. The Job To Be Done for each of the three personas.
6. Proposed solution and architecture.
7. Results of the previous defence.
8. Current sprint focus and validation: user findings, product hypotheses, and technical hypotheses under test.
9. Demo for the first persona. In later sprints, validate the next persona.
10. Comparison with alternatives.
11. Metrics.
12. Measurement economics for tariff calculation.
13. Next-sprint plan.
14. Technology stack.
15. Team.

Keep completed findings, planned validation, and technical work in progress visibly separate. Do not present a planned test or a local simulation as a completed user or production result.

## Done

Every slide has a purpose, evidence source, speaker text, and review status.
